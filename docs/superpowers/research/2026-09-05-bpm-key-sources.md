Raw output of a research workflow (4 researchers, 4 skeptics with live probes, 1 synthesis). The synthesis is first; verdicts and per-source details follow. Reference material for the BPM/key feature; the design spec, once written, is the authority.

# BPM and key ("note") for the DJ app — research brief

Date: 2026-09-05. Scope: free sources of BPM and musical key for the owner's Spotify tracks, usable from a browser-only static Preact app on GitHub Pages (no server, no secrets), house/techno first. Facts below were probed on 2026-09-04/05 and cross-checked by a second reviewer; refuted claims are dropped, unsettled ones are in section 6.

## 1. The short answer

1. Spotify itself is closed for good: development-mode apps lost audio features and previews on 2024-11-27, and since May 2025 extended quota is granted to organisations only (250k MAU). No free API gives Beatport-grade BPM+key by ISRC; Beatport's own API needs a login-gated OAuth client.
2. The best zero-effort option is ReccoBeats (api.reccobeats.com): no key, CORS-open, free for personal and commercial use, returns Spotify's exact tempo/key/mode/energy for up to 40 Spotify ids or ISRCs per call, covered 45–62% of probed electronic tracks including 2026 releases.
3. The most trustworthy source for tracks the DJ owns is their own DJ software: one rekordbox XML (or Traktor NML, Serato, Engine, VirtualDJ) export, parsed in the browser, zero terms risk. Since rekordbox 7.2.16 (July 2026) Spotify Premium tracks can even sit in a rekordbox collection.
4. Gaps can be filled by computing BPM+key in the browser from Deezer's 30-second previews (ISRC lookup via JSONP, CORS-open MP3; a real techno test gave 134.92 BPM / F minor against a 134.99 / F minor reference), at the cost of Deezer's non-commercial terms and an AGPL licence if essentia.js is used.
5. Recommendation: ship the ReccoBeats lookup first (about 125 requests for 5,000 tracks), add the DJ-library import second, keep preview analysis and AcousticBrainz as opt-in fillers; cache everything per track in IndexedDB with source and confidence, and let the owner override.

Rejected (one line each):

- Spotify Web API audio-features / preview_url: removed for dev-mode and new apps since 2024-11-27; extended quota is organisations-only; `GET /tracks` batch gone Feb 2026 (ISRC in `external_ids` survives, reverted March 2026).
- Beatport API v4: best data for the genre, but 401 without an OAuth Bearer token and the developer portal only offers "Login with Beatport"; beatport.com pages are bot-protected.
- Tunebat (API partner-only via Songstats), songdata.io, Musicstax, Chosic: Cloudflare-gated front-ends over Spotify data, no programmatic path.
- TheAudioDB: CORS * and no key, but 8–9 of 10 house/techno tracks absent and the rest had null tempo/key.
- Apple Music, Last.fm, Discogs, ListenBrainz, Hooktheory: no per-track BPM or key at all.
- SoundCloud: `bpm`/`key_signature` fields exist but are uploader-entered and sparse; every endpoint needs an OAuth token.
- Cyanite (about 290 EUR/month), Musiio (absorbed by SoundCloud): paid, server-side.
- YouTube: terms forbid extraction; no CORS media.
- Anna's Archive 255M-row scrape and its Hugging Face mirrors (ozefe, monology, weebnan, Gildas 56M): fetched after the deprecation by scraping, redistribution forbidden by Spotify terms, 4–18 GB; do not use or re-host. HF dataset-viewer `/filter` on them is partial (first 5 GB) and flaky.
- Hosting a multi-million-row feature table on GitHub Pages (1 GB cap) or GitHub Releases (no CORS): both technically and legally the worst option.
- rekordbox `master.db`: has ISRC and key, but SQLCipher-encrypted; would mean shipping AlphaTheta's key in a public site.
- djay Pro: no documented collection export. keyfinder-js (no licence, dead 2017), libkeyfinder-wasm (GPL, 0 stars, July 2026): not worth the risk.

## 3. Recommended approach

### 3.1 Source tiers

Resolve BPM and key independently per track; the first tier that has a value wins, later tiers are kept for the expansion view.

1. Owner override (manual edit) — always wins.
2. DJ software import (rekordbox/Traktor/Serato/Engine/VDJ/Mixxx) — confidence high.
3. ReccoBeats (Spotify's numbers) — confidence high; also the only source of energy.
4. File tags (TBPM/TKEY) when local files are imported — high if written by DJ software.
5. In-browser analysis of a Deezer preview or local file — medium; downgraded to low when the two BPM estimators disagree or key strength is below ~0.6.
6. AcousticBrainz — low.
7. Deezer `bpm` field (BPM only) — low.

### 3.2 Matching strategy

- ISRC first. The app already holds `external_ids.isrc`. ReccoBeats accepts ISRCs directly (prefer them over Spotify ids to minimise transfer of Spotify identifiers), Deezer has `/track/isrc:{ISRC}`, MusicBrainz has `/ws/2/isrc/{ISRC}`, file tags may carry TSRC. Validate every ISRC hit by comparing title and duration (a junk ISRC once returned a real Deezer track).
- DJ exports have no ISRC or Spotify id (one untested exception: Spotify tracks in rekordbox ≥7.2.16). Use normalised title+artist with duration tie-break:
  - Normalise: NFD, strip diacritics, lowercase, remove punctuation, collapse spaces, drop "feat./ft. …", drop "(original mix)" / "- original mix" and "extended mix" / "radio edit" suffixes but keep remix names as a separate `mix` field ("(X Remix)").
  - Build two keys per side: `title|mix|primaryArtist` and `title|primaryArtist`. Match the full key first, then the base key; when several candidates remain, pick the one whose duration is within ±2 s (rekordbox `TotalTime` is whole seconds, Traktor `PLAYTIME_FLOAT` is float, Spotify `duration_ms`/1000).
  - Artists: split on ",", "&", " x ", "feat"; compare the primary token, then token Jaccard ≥0.5 for multi-artist strings.
  - Keep unmatched rows in a "review" list for manual linking (search-as-you-type against the Spotify library).
- Streaming-history rows already carry Spotify URIs, so they join on track id directly.

### 3.3 What the owner has to do

- ReccoBeats: nothing; press "Look up".
- rekordbox: optionally set Preferences > View > Key display format to Alphanumeric (Camelot in the export; the importer handles Classic too), make sure the tracks are in at least one playlist (the manual says "track information in these playlists"), then [File] > [Export Collection in xml format], drop the .xml into the app.
- Traktor: right-click Track Collection > Export the Collection (or copy `Documents/Native Instruments/Traktor x.y.z/collection.nml`).
- Serato: copy `~/Music/_Serato_/database V2`. Engine DJ: copy `Engine Library/Database2/m.db` with Engine closed. VirtualDJ: `Documents/VirtualDJ/database.xml`. Mixxx: `mixxxdb.sqlite`.
- Preview analysis: nothing except accepting a notice about Deezer's terms; laptop recommended, leave the tab open.
- Phone: import the "enrichment pack" JSON exported from the laptop through the existing zip import.

### 3.4 What runs in the browser

- Lookups: `fetch` for ReccoBeats, MusicBrainz, AcousticBrainz; `<script>` JSONP for Deezer (`?output=jsonp&callback=`).
- Parsing: rekordbox/VDJ XML with DOMParser (all needed data are attributes); Traktor as a chunked text scan per `<ENTRY …>…</ENTRY>` in a Worker; Serato as a DataView TLV reader with `TextDecoder('utf-16be')`; Engine/Mixxx with sql.js in a Worker (self-host `sql-wasm.wasm`).
- Analysis: decode with `OfflineAudioContext({sampleRate: 44100}).decodeAudioData` (guarantees the 44.1 kHz essentia needs; downmix to mono manually; the input ArrayBuffer is detached, slice first), then in a Worker pool: BPM via essentia `RhythmExtractor2013` (degara for speed, multifeature when a confidence value is wanted) cross-checked with `PercivalBpmEstimator`, key via `KeyExtractor(..., profileType: 'edma')`. MIT alternative: web-audio-beat-detector `analyze()` (fractional BPM) + `@audio/mir-key` with EDM profiles (unproven, needs validation). For local MP3s, decode a ~2 MB byte slice from ~40% in (verified to work; not for FLAC/M4A). AIFF cannot be decoded by Chrome; needs a small PCM parser.
- Nothing leaves the browser except the lookup requests above.

### 3.5 Request budgets and rate limits (5,000-track library)

- ReccoBeats: 40 per call → 125 calls; run at 1 call/s with exponential back-off on 429 (honour Retry-After) → about 2–3 minutes. Parse responses defensively; log coverage.
- Deezer API: queue at ≤8 requests/s (observed quota about 50 per 5 s, no rate-limit headers, errors arrive as HTTP 200 bodies with `error.code` 4) → about 10–12 minutes for 5,000 ISRC lookups; treat `bpm: 0` as unknown; preview URLs expire 15 minutes after issue, so fetch and analyse immediately and store only results.
- Analysis: 0.4–1.2 s per 30 s clip depending on hardware (0.5 s claimed on one desktop, 1.2 s measured on an i5-12400 in Chromium); 5,000 clips ≈ 40 minutes to 2 hours single-threaded, divide by the Worker count. Resumable, runs in the background.
- MusicBrainz: 1 request/s per IP, batch 10–20 ISRCs per `recording?query=isrc:(A OR B …)` call → 250–500 requests ≈ 4–8 minutes; browsers cannot set the requested User-Agent, tolerated in tests. AcousticBrainz: 25 MBIDs per bulk call at ≤1 call/s → a few minutes. Never add `inc=recordings` to the isrc endpoint (400).
- Spotify: no new calls needed; the ISRC is already in the local library.

### 3.6 Cache (IndexedDB)

- Store `features` keyed by Spotify track id: `{ trackId, isrc, bpm, bpmConfidence, key: { pitchClass, minor }, camelot, keyStrength, energy, source, sourceDetail, fetchedAt, matchedBy }` — the resolved value.
- Store `featureSources` keyed by `trackId + source`: every raw value obtained, so the expansion can show disagreements and a later re-resolution needs no new requests.
- Store `lookupState` keyed by `trackId + source`: `notFound` with a `retryAfter` date (e.g. 90 days for ReccoBeats, never for frozen AcousticBrainz) to avoid re-querying.
- Store `overrides` keyed by track id (owner edits, with a note), never overwritten by imports.
- Export/import all four stores as `features.json` inside the existing zip format so the laptop's work moves to the phone.
- Keep the cache limited to the owner's own tracks (no library-wide harvesting), which is the lowest-exposure pattern under Spotify's terms.

### 3.7 Provenance and confidence per track

- Every value carries `source` (`rekordbox`, `traktor`, `serato`, `engine`, `reccobeats`, `tag`, `analysis-preview`, `analysis-file`, `acousticbrainz`, `deezer-bpm`, `manual`) and a three-level confidence.
- High: DJ software, ReccoBeats/Spotify, manual. Medium: analysis with degara and Percival within 1% (after octave folding) and key strength ≥0.6. Low: AcousticBrainz, Deezer `bpm`, analysis with disagreements or strength <0.6.
- Show low confidence visually (dotted badge border or "?" suffix), medium plain, high with a small check in the expansion. Flag likely half/double-time when the value is outside 110–150 BPM for house/techno and offer ×2 / ÷2 with one tap. For keys, show the relative key as an alternative when strength is weak (edma vs bgate flipped between F minor and Ab major on the same clip).

### 3.8 Camelot mapping

Canonical internal form: pitch class 0–11 (C = 0) plus `minor` boolean; display Camelot, classic name and Open Key from it.

|---|---|---|---|---|---|
| 1A / 1B | 6m / 6d | Ab minor / B major | 8,0 / 11,1 | 11 / 10 | 20 / 11 |
| 2A / 2B | 7m / 7d | Eb minor / F# major | 3,0 / 6,1 | 13 / 12 | 15 / 6 |
| 3A / 3B | 8m / 8d | Bb minor / Db major | 10,0 / 1,1 | 15 / 14 | 22 / 1 |
| 4A / 4B | 9m / 9d | F minor / Ab major | 5,0 / 8,1 | 17 / 16 | 17 / 8 |
| 5A / 5B | 10m / 10d | C minor / Eb major | 0,0 / 3,1 | 19 / 18 | 12 / 3 |
| 6A / 6B | 11m / 11d | G minor / Bb major | 7,0 / 10,1 | 21 / 20 | 19 / 10 |
| 7A / 7B | 12m / 12d | D minor / F major | 2,0 / 5,1 | 23 / 22 | 14 / 5 |
| 8A / 8B | 1m / 1d | A minor / C major | 9,0 / 0,1 | 1 / 0 | 21 / 0 |
| 9A / 9B | 2m / 2d | E minor / G major | 4,0 / 7,1 | 3 / 2 | 16 / 7 |
| 10A / 10B | 3m / 3d | B minor / D major | 11,0 / 2,1 | 5 / 4 | 23 / 2 |
| 11A / 11B | 4m / 4d | F# minor / A major | 6,0 / 9,1 | 7 / 6 | 18 / 9 |
| 12A / 12B | 5m / 5d | C# minor / E major | 1,0 / 4,1 | 9 / 8 | 13 / 4 |

```js
// pitch class p (C=0), major boolean -> Camelot
const camelot = (p, major) =>
  `${((7 * p + (major ? 7 : 4)) % 12) + 1}${major ? 'B' : 'A'}`;
// Spotify/ReccoBeats: key -1 = unknown; mode 1 = major
// Open Key "10m" -> Camelot: number ((n + 6) % 12) + 1, d->B, m->A
// Traktor VALUE v: v < 12 ? major, p = v : minor, p = v - 12
// Engine key k (nullable, 0 = C major, test k !== null):
//   major = k % 2 === 0, number ((8 + (k >> 1) - 1) % 12) + 1
// Text: /^0?(1[0-2]|[1-9])([ABab])$/ Camelot (accept zero padding),
//       /^0?(1[0-2]|[1-9])([dm])$/ Open Key,
//       /^([A-Ga-g])([#♯b♭]?)\s*(m|min|minor|maj|major)?$/ classic
//       (enharmonics C#=Db, D#=Eb, F#=Gb, G#=Ab, A#=Bb), "" = unknown
```

Compatibility rules for the set builder: same code; same number, other letter (relative major/minor); ±1 number, same letter; optional "energy boost" +2 same letter. In Traktor files prefer `MUSICAL_KEY` over `INFO KEY` (tag text, stale in 3 of 18 real pairs).

## 4. Design sketch for the app

Badges on rows (Top, Playlist, Artist, Crate views)

- Two compact pills after the duration: `128` and `8A`. Key pill coloured by Camelot number on a 12-hue wheel; minor (A) filled, major (B) outlined. Low confidence: dotted border. Missing: nothing on the row (a faint dot only while a lookup is queued), so unenriched lists stay clean.
- Rows are sortable by BPM and by Camelot number once values exist; a header toggle switches key display between Camelot, Open Key and classic names ("note").

Track expansion

- One line: `BPM 128.0 · Key 8A (A minor) · Energy 0.81`, followed by `Source: Spotify via ReccoBeats · high` (or "rekordbox export 2026-09-01", "Analysed from 30 s Deezer preview", "AcousticBrainz, low").
- Secondary line when other sources disagree: `rekordbox says 127.98 · 8A`, `analysis says 4B (relative of 4A)`.
- Actions: Edit (BPM field, key picker on a small Camelot wheel), ×2 / ÷2, Re-analyse, Clear override.

"Keys" / Set builder view

- Top controls: seed track picker (prefills BPM and key) or a BPM range slider with a tolerance chip (±2%, ±4%, ±6%, custom range such as 122–130); "include half/double time" toggle; key mode: Off / Strict (same, relative, ±1) / Extended (+2 energy boost); source filter "high confidence only"; sort by play count, Spotify popularity, date added.
- Left: a small Camelot wheel with per-segment track counts; tapping a segment filters, compatible segments light up relative to the seed.
- Middle: candidate list with the same badges plus ΔBPM and key relation (same / relative / +1 / −1 / boost) relative to the seed or to the last track of the set.
- Right (or bottom sheet on phone): the set in progress, each transition annotated with ΔBPM % and key relation, warnings on jumps beyond the tolerance, total running time; export as text or copy track list (a Spotify playlist export can come later: dev mode still allows the owner's own account).

Import / lookup flow ("Enrich" screen, next to the existing zip import)

- Coverage card at the top: "BPM 3,120 / 4,980 · Key 2,870 / 4,980", broken down by source, with a "Export enrichment pack" button (JSON inside the zip, for the phone).
- Step 1 card "Look up Spotify audio data (ReccoBeats)": Run / Pause, progress "1,240 / 4,980 · found 62%", last run date, "retry not-found older than 90 days".
- Step 2 card "Import your DJ library": drop zone accepting .xml (rekordbox/VDJ), .nml, `database V2`, `m.db`, `mixxxdb.sqlite`; the app detects the format from the header; result summary "matched by ISRC 0 · by title+artist 3,410 · unmatched 590 · review" with a review list (export row on the left, suggested Spotify track on the right, search box, Link / Skip).
- Step 3 card "Analyse remaining tracks from 30-second previews" (opt-in): a short notice about Deezer's non-commercial terms and the analysis library's licence, "Laptop recommended", Worker count, progress with tracks per minute, Pause / Resume; runs while the owner browses other views.
- Step 4 card "AcousticBrainz fallback (low confidence)": one button, small print about 2022 cut-off.
- Settings: key notation (Camelot / Open Key / classic), BPM decimals (0 or 1), "hide low-confidence badges".

## 5. Risks and licences

- Spotify Developer Terms v10 (15 May 2025) and Policy: the app is an SDA. II.8 defines Spotify Content as any data "made available through the Spotify Platform"; IV.3.1 forbids storing, aggregating or building databases of Spotify Content "other than as strictly necessary to operate your SDA"; IV.2.5 forbids transferring Spotify Content, "including aggregate, anonymous or derivative data", to third parties; Policy III.13 says do not "analyze the Spotify Content" and III.9 restricts transferring data to other services. Whether third-party-relayed tempo/key numbers are Spotify Content, and whether bare numbers are protectable, is unsettled. Practical ranking, lowest to highest exposure: per-track cache of the owner's own library → live third-party lookups → in-app fetch of public datasets → re-hosting datasets. Stay in the first tier, send ISRCs rather than Spotify ids to third parties where possible, never publish the cache.
- ReccoBeats ToS (2026-05-25): free for personal and commercial use, but "aggregated from Spotify data… you are responsible for… third-party terms"; it claims a homemade analyser while values match Spotify exactly, so the Spotify exposure is laundered, not removed. Single maintainer, "may modify, suspend, or shut down". Mitigation: cache, treat as replaceable, no attribution clause found but credit it in the expansion anyway.
- Deezer Developer Terms: "strictly limited for a non-commercial purpose and in a non-commercial environment"; Content limited to "strictly private use within a family scope"; no bypassing protections "for the purpose of downloading the Content"; terms may change "at any time without any prior notice"; the docs say you must log in to accept the simple-API terms, which anonymous JSONP use has not done. A working DJ preparing paid sets is arguably commercial. No attribution clause found; Deezer's Trademark Guidelines apply only if the logo is used. JSONP and CDN CORS have been toggled before (CORS was broken and fixed in January 2025). Show the notice, make it opt-in, keep only derived numbers.
- AGPL-3.0 (essentia.js): a GitHub Pages bundle "conveys" the library to every visitor; the GNU FAQ states JavaScript served to visitors must come with source under the licence, and §5c licenses the combined work as a whole. Isolating essentia in a Worker is not an established safe harbour; the private repo would in effect become public under AGPL (or the owner buys MTG's commercial licence, offered for Essentia). Alternatives: web-audio-beat-detector (MIT, fractional BPM via `analyze()`), realtime-bpm-analyzer (Apache-2.0, integer BPM only), `@audio/mir-key` + `@audio/mir-chroma` (MIT, July 2026, unproven on EDM). libkeyfinder-wasm is GPL-3.0 with the same consequences.
- Engine confidence caveat: essentia degara returns confidence 0 by design; only multifeature (4–8× slower) yields one; Percival halves fast tempos (174 → 86.86). Key on 30 s clips worked in one test but is not benchmarked (GiantSteps evaluates on 2-minute previews).
- AcousticBrainz/MusicBrainz: CC0 data, no attribution required (credit anyway); AB may go offline any time; MusicBrainz asks for a meaningful User-Agent that browsers cannot set; keep to 1 request/s.
- GetSongBPM (if adopted): the free key ships in the public bundle (anyone can burn the 3,000/h quota); a visible backlink is mandatory or the account is suspended; content-type is `text/html` despite JSON bodies.
- Datasets: Kaggle/HF uploader licences (ODbL, CC BY-NC, "Unknown", "spotify-developer-terms") are asserted by people who do not own the data; Kaggle's terms contain an anti-scraping clause (not re-verified); the Anna's Archive corpus is an unauthorised post-deprecation scrape. Do not re-host any of it.
- DJ exports: VDJ `Scan Bpm` must be converted (60 / value); Engine `key` 0 is C major (test `!== null`); rekordbox `Tonality` may be empty or raw tag text; Traktor `INFO KEY` can be stale; Serato `tkey` notation unverified. Rekordbox streaming-track restrictions do not list XML export, but the export of Spotify tracks and their `Location` format is untested.
- Platform: iOS Safari has `webkitdirectory` only from 18.4 and no `showDirectoryPicker`; Chrome cannot decode AIFF; a 6-minute stereo decode is ~127 MB, so analyse windows, not whole tracks, on phones. GitHub Pages: 1 GB site cap, public origin, no secrets ever.

- Same idea at file level: music-metadata (MIT, 11.15.0) common tags (https://github.com/Borewit/music-metadata/blob/master/doc/common_metadata.md) include `bpm` (ID3 TBPM, Vorbis BPM, MP4 TMPO, ASF WM/BeatsPerMinute) and `key` ('The Initial key frame contains the musical key in which the sound starts' — TKEY, Vorbis KEY, WM/InitialKey) plus `isrc`; files tagged by Mixed In Key/rekordbox often carry these, so read tags first and only run DSP on the remainder.
- Essentia key-profile choice matters more than window length: Key docs (https://essentia.upf.edu/reference/std_Key.html) — default profileType is `bgate`; "'edma' - automatic profiles extracted from corpus analysis of electronic dance music [3]. They normally perform better that Shaath's"; 'edmm' is the manually tweaked variant; `useMajMin` 'use a third profile called majmin for ambiguous tracks … Only available for the edma, bgate and braw profiles'. On the Doppler preview bgate gave Ab major while edma gave F minor (matching AcousticBrainz). KeyExtractor's positional JS signature is (audio, averageDetuningCorrection, frameSize, hopSize, hpcpSize, maxFrequency, maximumSpectralPeaks, minFrequency, pcpThreshold, profileType, …) — profileType is the 10th argument.
- RhythmExtractor2013 'confidence' is meaningless for degara: docs say 'confidence (real) - confidence with which the ticks are detected (ignore this value if using degara method)'; every degara run returned 0. If a confidence badge is wanted, multifeature (4–8× slower) is required, or use agreement between degara and PercivalBpmEstimator instead. PercivalBpmEstimator showed an octave error at 174 BPM (returned 86.86), so cap/uncap min/max tempo per genre.
- Chromium decodeAudioData accepts arbitrary MP3 byte slices (bytes 100,000–300,000 of a 128 kbps MP3 decoded to 12.49 s of audio) — the slice trick is MP3-specific; WAV/FLAC/AIFF slices need header-aware handling, and AIFF needs a JS parser regardless.
- Deezer preview CDN returns `cache-control: public, max-age=12150234` (~140 days) but the URL is signed for 15 minutes (`hdnea=exp=…`), so previews cannot be re-fetched later from a stored URL; the track id must be re-resolved through the (non-CORS, JSONP-only) API each time.
- Beatport API v4 (the best ground truth for house/techno BPM+key) is CORS-open but not keyless: https://api.beatport.com/v4/catalog/tracks/?name=Doppler → 401 {"detail":"Authentication credentials were not provided."} with `access-control-allow-origin: *` and `www-authenticate: Bearer realm="api"` — needs an OAuth client, i.e. a secret that cannot live in a static site. GetSongBPM (api.getsong.co) likewise: 401 'Invalid API Key, or inactive.' with ACAO * — CORS-open, free key required; its terms page (getsongbpm.com/api) is behind Cloudflare (403), so attribution/backlink rules were not verifiable.
- Spotify dev-mode changes since the researcher's cut-off that affect the ISRC pipeline: February 2026 changelog marked Track `external_ids` as REMOVED, then March 2026 changelog: '[REVERTED] external_ids — Known external IDs for the track … will continue to be available'; Search `limit` max is now 10 (default 5); July 2026: quota is per developer account across all client IDs, 429 body reason 'QUOTA_EXCEEDED'. Keep relying on ISRC from Get Track, not on Search.
- Essentia.js maintenance reality check: npm registry shows the last publish 0.1.3 on 2021-06-24 and GitHub tags stop at v0.1.3, though the repo was pushed 2025-12-10 (not archived, 867 stars). Measured bundle: essentia-wasm.web.wasm 1.9 MB, essentia-wasm.web.js 216 KB, essentia.js-core.es.js 320 KB (min 40 KB). essentia-wasm.web.js is a classic script defining a global factory; `EssentiaWASM()` returns a Promise of the module (used that way in the Chromium probe).

### Deezer 30-second previews + in-browser audio analysis (Web Audio API + a JS BPM/key library) — fit: strong (verified-probe)
- Gives: Not a data API: compute BPM and key yourself, in the browser, from the 30 s MP3 preview that the Deezer track object exposes (`preview`). - Status 2026: Works on 2026-09-04.

Cost: CPU time (~a few hundred ms to a couple of seconds per 30 s clip) and licence choice for the key detector. ### Rekordbox 6/7 — Collection XML export (DJ_PLAYLISTS format v1.0.0) — fit: strong (verified-official)
- Gives: Per <TRACK> (all data are XML attributes, no child text): AverageBpm (float, 2 decimals, e.g. AverageBpm="128.00"; the official PDF's 'Unit: Second' is a doc slip, the value is BPM), Tonality (utf-8 string, 'Tonality (Kind of musical key)'; real sample from rekordbox 6.6.2: Tonality="Fm"; empty string when unanalysed), TotalTime (integer seconds, e.g. TotalTime="172"), Name, Artist, Album, Remixer, Label, Mix, Genre, Comments, Location (file URI 'file://localhost/C:/Music/...%20...'), Kind, Size, BitRate, SampleRate, DateAdded, PlayCount, Rating, Colour. ### Serato DJ Pro — _Serato_/database V2 (binary) + _Serato_/Subcrates/*.crate — fit: possible (verified-secondary)
- Gives: database V2 is a flat sequence of TLV records: 4-ASCII-char tag, uint32 big-endian length, payload; each track is an 'otrk' container whose children include tsng (title), tart (artist), talb (album), tgen (genre), tbpm (BPM as TEXT), tkey (key as TEXT, e.g. what Serato displays), tlen (length as text), tbit, tsmp, ttyp (file type), pfil (path relative to drive root), tadd/uadd (date added), bbgl (beatgrid locked), bmis (missing). Field type = first letter: t/p = UTF-16BE text, u = uint32 BE, s = uint16 BE per Holzhaus' parser, b = 1-byte bool, o/r = nested records; 'vrsn' header is text. .crate files use the same TLV scheme: vrsn, osrt/tvcn/brev (sort), ovct/tvcn/tvcw (columns), otrk > ptrk (track path). No energy, no ISRC. Serato additionally stores BPM (as ASCII text, e.g. '115.00') inside a 'Serato Autotags' GEOB frame in the audio file, but key is not in a Serato GEOB; it is in the database tkey field (and whatever key tag the file carries).
- Match: No ISRC. tsng + tart normalised; tlen (text length) vs duration as tie-breaker; pfil file name as fallback.
- Access: Free, local file, but there is NO official export; the DJ copies ~/Music/_Serato_/database V2 (Mixxx importer looks in the standard Music folder and at the root of external drives, folder '_Serato_', file 'database V2', crates in 'Subcrates'). Serato support articles were unreachable (HTTP 403/429 from this environment). Browser parsing is straightforward: File.arrayBuffer() → DataView loop, TextDecoder('utf-16be') for t*/p* fields; no library needed. Key notation in tkey follows the user's Serato display setting (not verified).
- Status 2026: Alive (Serato DJ Pro 3.x); format documented by reverse engineering (Mixxx wiki, Holzhaus/serato-tags MIT scripts, SpinTools/seratoparser, chrisle/serato-connect Node-only).
- Notes: Parser essence (Holzhaus, MIT): header = struct('>4sI'); text fields decode as (data[1:] + b'\x00').decode('utf-16') i.e. skip a leading byte then UTF-16BE; tag list: vrsn Version, otrk Track, ttyp File Type, pfil File Path, tsng Song Title, tlen Length, tbit Bitrate, tsmp Sample Rate, tbpm BPM, tadd/uadd Date added, tkey Key, bbgl Beatgrid Locked, tart Artist, utme File Time, bmis Missing; crates: osrt Sorting, brev Reverse Order, ovct Column Title, tvcn Column Name, tvcw Column Width, ptrk Track Path. ### Audio-file tags (ID3v2 TBPM/TKEY, Vorbis BPM/KEY|INITIALKEY, MP4 tmpo) read in-browser with music-metadata, or exported as CSV by Mp3tag / beets — fit: possible (verified-official)
- Gives: ID3v2.3/2.4: TBPM 'contains the number of beats per minute ... The BPM is an integer and represented as a numerical string'; TKEY 'Initial key ... string with a maximum length of three characters. The ground keys are represented with A,B,C,D,E,F,G and halfkeys with b and #. Minor is represented as m' (so 'Fm', 'F#m', 'Bb'). FLAC/Ogg Vorbis comments: BPM; key as KEY (music-metadata mapping) or INITIALKEY (Mp3tag mapping) — read both. MP4/M4A: tmpo atom = BPM; neither Mp3tag's table nor music-metadata's common-tag table lists any MP4 atom for key (only freeform vendor atoms, not standardised). Coverage = only files that a DJ tool or tagger has written key/BPM into.
- Match: Read title/artist from the same tags (common.title, common.artist) and duration from the container; then the same title+artist+duration matching. No ISRC unless the tagger wrote TSRC.

### Key notation mapping: classic names ↔ Open Key (Traktor) ↔ Camelot (rekordbox Alphanumeric / MIK) ↔ Engine int ↔ Traktor int — fit: strong (verified-secondary)
- Gives: Full 24-row table (Camelot | Open Key | major/minor names | Engine key int | Traktor MUSICAL_KEY int): 1A|6m|Ab minor (G#m)|11|20 · 1B|6d|B major|10|11 · 2A|7m|Eb minor (D#m)|13|15 · 2B|7d|F# major (Gb)|12|6 · 3A|8m|Bb minor (A#m)|15|22 · 3B|8d|Db major (C#)|14|1 · 4A|9m|F minor|17|17 · 4B|9d|Ab major (G#)|16|8 · 5A|10m|C minor|19|12 · 5B|10d|Eb major (D#)|18|3 · 6A|11m|G minor|21|19 · 6B|11d|Bb major (A#)|20|10 · 7A|12m|D minor|23|14 · 7B|12d|F major|22|5 · 8A|1m|A minor|1|21 · 8B|1d|C major|0|0 · 9A|2m|E minor|3|16 · 9B|2d|G major|2|7 · 10A|3m|B minor|5|23 · 10B|3d|D major|4|2 · 11A|4m|F# minor (Gbm)|7|18 · 11B|4d|A major|6|9 · 12A|5m|C# minor (Dbm)|9|13 · 12B|5d|E major|8|4. Conversion rules: Open Key number = Camelot number + 5 (wrap 1..12); Camelot number = Open Key number − 5 (wrap); letters A↔m (minor), B↔d (major) (Mixxx: 'Lancelot notation is OpenKey notation rotated counter-clockwise by 5'). Camelot compatibility for set building: same code, same number other letter (relative major/minor), ±1 number same letter; energy boost +2 same letter is a common extra rule.
- Match: Normalise every incoming key string to one canonical form: (a) regex ^(1[0-2]|[1-9])([ABab])$ → Camelot; (b) ^(1[0-2]|[1-9])([dm])$ → Open Key → Camelot; (c) ^([A-Ga-g])([#♯b♭]?)\s*(m|min|minor|maj|major)?$ → pitch class + mode → Camelot (treat enharmonics: C#=Db, D#=Eb, F#=Gb, G#=Ab, A#=Bb; Mixxx's parser regex accepts the same shapes); (d) integers from Engine (Camelot order) or Traktor (chromatic order) via the table.
- Access: Pure data, no dependency.
- Status 2026: Stable conventions.
- Notes: Three independent sources agree: Mixxx keyToOpenKeyNumber (C/Am=1, G/Em=2, D/Bm=3, A/F#m=4, E/C#m=5, B/G#m=6, F#/Ebm=7, Db/Bbm=8, Ab/Fm=9, Eb/Cm=10, Bb/Gm=11, F/Dm=12) with Lancelot = OpenKey−5; openkeyscan's published 24-row Camelot/Open Key list; libdjinterop's Engine enum (0=C,1=Am,2=G,3=Em,...,23=Dm). Traktor ints come from the 8 sample pairs (INFO KEY text vs MUSICAL_KEY VALUE), all consistent with 0=C major chromatic, 12=C minor chromatic. Rekordbox 'Classic' spellings and Serato/VDJ text spellings were not enumerated by official docs — rely on the generic regex.
- Evidence: https://raw.githubusercontent.com/mixxxdj/mixxx/main/src/track/keyutils.cpp, https://raw.githubusercontent.com/mixxxdj/mixxx/main/src/proto/keys.proto, https://www.openkeyscan.com/camelot-wheel-explained, https://raw.githubusercontent.com/xsco/libdjinterop/main/include/djinterop/musical_key.hpp, https://raw.githubusercontent.com/polamjag/traktor-nml/6bdee551aceb5ce462da26e85ba2961aedcffc00/spec/traktor/traktor-nml-demo.nml

Verified present in the TS bindings (src/typescript/core_api.ts, 202 methods) AND working in the WASM runtime (2.1-beta6-dev, 199 algorithms): RhythmExtractor2013(signal, maxTempo=208, method='multifeature'|'degara', minTempo=40) -> {bpm, ticks, confidence[0..5.32], estimates, bpmIntervals}; PercivalBpmEstimator(signal) -> {bpm}; BeatTrackerMultiFeature / BeatTrackerDegara -> {ticks[, confidence]}; KeyExtractor(audio, ..., profileType='bgate') -> {key, scale, strength}; Key(pcp) -> {key, scale, strength, firstToSecondRelativeStrength}; HPCP; LoopBpmEstimator; Danceability. profileType options include EDM-specific profiles 'edma', 'edmm' (Faraldo et al. 2016), 'braw', 'bgate' (Faraldo 2017, Beatport corpus). Gives fractional BPM (e.g. 128.01) and key+scale -> trivially mapped to Camelot. Constraint from docs: RhythmExtractor2013 'requires the sample rate of the input signal to be 44100 Hz'. Measured (my probe, synthetic 128 BPM / A-minor track, Chromium 147 headless on a 12-core desktop): 60 s window -> degara 360 ms, multifeature 1599 ms (conf 3.86), Percival 645 ms, KeyExtractor(edma) 78 ms; full 360 s -> degara 1423 ms, multifeature 8093 ms, Percival 3645 ms, KeyExtractor 441 ms. Node 24 numbers were the same order (30 s: multifeature 876 ms, degara 178 ms, Percival 334 ms, Key 54 ms). All returned 128.0x BPM and 'A minor' (strength 0.85 with edma). Published benchmarks: ISMIR 2020 paper measured a Xiaomi Redmi Note 7 Pro (Snapdragon 1.7 GHz) and found Android Chrome 'considerably slower' than Linux Chrome (no numeric ratio in text); TISMIR 2021: on 30 s segments most algorithms took 0.46-3.48 s.
- Match: Not a lookup service: input is decoded audio. Flow: File -> ArrayBuffer -> OfflineAudioContext({sampleRate:44100}).decodeAudioData -> getChannelData(0) (or manual L/R average) -> essentia.arrayToVector -> RhythmExtractor2013 / KeyExtractor in a Web Worker; results then attached to the Spotify track matched by tags (see music-metadata entry).
- Access: Free, open source, no key, fully client-side (a static site can host the .wasm). Licence AGPL-3.0 (package.json, GitHub). Bundle (npm 0.1.3 dist, jsDelivr file sizes): essentia-wasm.web.wasm 1.99 MB + essentia-wasm.web.js 0.22 MB + essentia.js-core.es.min.js 0.04 MB (~2.3 MB uncompressed; ES build essentia-wasm.es.js 2.56 MB embeds the wasm). Also sold under a commercial licence by MTG. Docs recommend running costly algorithms in a Web Worker or AudioWorklet and deleting output vectors (.delete()) to avoid leaks. essentia-wasm.web.js is a classic (non-module) script exposing a global EssentiaWASM() factory; import() of it fails (verified).
- Status 2026: Alive but slow-moving: npm latest 0.1.3 published 2021-06-24 (no newer npm release); GitHub MTG/essentia.js last push 2025-12-10, not archived, 867 stars; GitHub 'latest release' API returns Not Found (no formal releases). Works on Node 24 and Chromium 147 as of 2026-09-05 (probe).
- Notes: Licence implication (analysis, not legal advice): a GitHub Pages site conveys the minified bundle to every visitor ('convey' = 'any kind of propagation that enables other parties to make or receive copies', AGPL s.0), so the app that links essentia.js is distributed as a combined work and must be offered with its Corresponding Source under AGPL-compatible terms; s.13 additionally requires a modified version offered over a network to provide its source. Practical consequence: the app repo (currently private) would need to be public/AGPL-licensed if essentia.js ships in it. Loading from a CDN does not change that materially. If the owner wants to keep the repo private, prefer MIT/Apache libraries (see web-audio-beat-detector + @audio/mir-key). 30-second window: enough for BPM on constant-tempo house/techno (30 s probe gave 128.01 with multifeature confidence 3.94), but key estimation for EDM is conventionally evaluated on 2-minute Beatport previews (GiantSteps key dataset: 604 two-minute previews), so use >=60-120 s from the middle of the track for key. Memory: a 6-minute 44.1 kHz stereo decode is 127 MB of Float32 (measured), and arrayToVector copies a mono channel (63 MB) into the WASM heap; analyse a window rather than the whole track on phones.

### Recommended end-to-end flow and time budget for 5,000 local tracks (synthesis of the probes) — fit: strong (verified-probe)
- Gives: Flow: (1) folder pick (webkitdirectory / showDirectoryPicker) -> (2) music-metadata.parseBlob on each file: take TBPM/TKEY if present, collect TSRC/title/artist/duration -> (3) match to the Spotify catalogue already in the app: exact ISRC first, then normalised title+artist with duration within +/-2 s -> (4) for unmatched-BPM/key files: read a ~2 MB slice from ~40% of the MP3 (whole file for FLAC/WAV/M4A), decodeAudioData in an OfflineAudioContext({sampleRate:44100}), mono-mix, essentia RhythmExtractor2013('degara' or 'multifeature' when confidence matters) + KeyExtractor(profileType 'edma' or 'edmm') on a 60-120 s window inside a Web Worker pool -> (5) persist {spotifyId, bpm, key, scale, camelot, confidence, source: 'tag'|'analysis'|'deezer'} in IndexedDB and export to the app's JSON/zip. Measured per-track cost on a desktop Chromium 147: MP3 slice decode 0.07 s + degara(60 s) 0.36 s + Key 0.08 s ~ 0.5 s (multifeature instead of degara: ~1.7 s); full-track decode path: 0.6 s decode + degara 1.4 s + Key 0.44 s ~ 2.5 s, or ~9 s with multifeature on the whole track.
- Match: ISRC (TSRC tag) -> Spotify external_ids.isrc; fallback title/artist/duration.
- Access: Everything runs client-side with MIT/Apache libraries except essentia.js (AGPL) - choose essentia only if the repo can be public.
- Status 2026: Estimates computed 2026-09-05 from the probes above.
- Notes: 5,000 tracks on the laptop: slice+degara+key path ~0.5 s/track -> ~40 min single worker, ~10-15 min with 4 workers; full-decode+multifeature path ~9 s/track -> ~12 h (too slow, avoid). Open questions:
- What formats and encoders make up the owner's library (MP3 vs FLAC vs AIFF vs M4A, and average duration)? AIFF share decides whether a JS PCM parser is needed; FLAC/WAV share decides I/O volume because the byte-slice trick was only verified for MP3.
- Do the owner's files already carry TBPM/TKEY (and TSRC) frames written by rekordbox, Serato, Traktor or Mixed In Key? If yes, most of the 5,000 tracks need no audio analysis at all - check a sample with music-metadata before building the analysis pipeline.
- Real-world accuracy: all timing/accuracy probes used a synthetic 128 BPM / A-minor signal. A validation set of ~50 real tracks with trusted BPM/key (rekordbox or Mixed In Key exports) is needed to choose between degara vs multifeature, Percival, and between bgate/edma/edmm key profiles, and to set confidence thresholds for the badges.
- Phone performance factor: no direct measurement on a mid-range Android device; the ISMIR 2020 paper says 'considerably slower' than a laptop without a ratio. Run bench.html-style timing on the owner's phone (also to check memory for 8-10 minute techno tracks, ~170-210 MB decoded stereo).
- Licensing decision: is the owner willing to make the app repository public under AGPL-3.0 (or buy MTG's commercial licence) to ship essentia.js? Otherwise the MIT/Apache stack must be used and its EDM key accuracy validated.
- Is using Deezer's track.bpm field and/or analysing Deezer previews acceptable to the owner given Deezer's non-commercial, private-use terms (the DJ presumably plays paid gigs), and does Deezer require accepting the developer terms/login before using the 'simple API' even though it answers without a key today?
- Does preview_url come back null on the single Get Track endpoint for development-mode apps (community reports could not be read: HTTP 403)? Irrelevant if the local-file path is adopted, but it settles whether any Spotify audio exists.
- Has essentia.js master (last push 2025-12-10, Emscripten update issue #133 closed 2024-01) got a newer, faster or SIMD-enabled build than npm 0.1.3 (2021)? Building from master could shrink the 2 MB wasm to only the needed algorithms (configure_bindings.py supports include lists).
- Can byte-slice decoding be made to work for FLAC (prepend STREAMINFO header) and M4A (needs moov atom), or must those files be decoded in full? Untested.
- Should Camelot-compatibility filtering use key strength / firstToSecondRelativeStrength thresholds to hide low-confidence keys, and how will manual overrides by the DJ be stored alongside computed values?
